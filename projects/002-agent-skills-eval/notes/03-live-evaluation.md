# 真实模型评测：从“程序跑通”到“Skill 真的有效”

## 当前准备情况

已提供 [refund-review Skill](../fixtures/refund-review/SKILL.md)、[6 个试验用例](../fixtures/refund-review/evals/evals.json)和[可选运行器](../src/live-eval.mjs)。本次仅验证加载、格式和运行器的无调用入口，**未执行真实模型评测，也未验证外部服务的具体兼容性**。

六个用例覆盖：符合条件、超过期限、信息缺失、商品已拆封、质量问题例外、第七天边界与无执行权限。每个用例有两条检查条件，共 12 条。它们是本项目自拟的入门样本，不是经过验证的业务基准。

所有政策和订单事实写在 prompt 内，不使用 files，让两组获得同一任务数据。Skill 增加的是处理步骤、信息缺失策略和输出约束。评分条件直接包含必要事实，减少默认裁判缺少原始输入造成的歧义。

## 可选运行

在子项目目录内，先完成 npm run setup。在当前终端设置以下环境变量；不要将密钥写入项目文件。

```powershell
$env:EVAL_BASE_URL = '你的兼容接口地址，以 /v1 结尾'
$env:EVAL_API_KEY = '你的接口密钥'
$env:EVAL_TARGET = '被测模型标识'
$env:EVAL_JUDGE = '裁判模型标识'
$env:EVAL_REPEATS = '5'
npm run live -- --run
```

只有显式传入 --run 才会发起请求。单独运行 npm run live 只显示说明。

脚本使用上游兼容接口 Provider。两种模型当前使用同一入口和密钥；如需不同供应商，应分别配置两个 Provider。脚本不强制采样参数，以避免不同模型参数支持差异；正式对比需要明确记录可用的 temperature、seed 等设置。

默认 5 轮，每轮 6 个任务、每任务两种模式，通常需要 **60 次目标调用 + 60 次裁判调用**。失败重试会增加请求，实际费用取决于指定服务。不要把上游报告的目标 Token 当成两类调用的总账单。

结果保存在独立的 artifacts/live/run-*/ 下，包括每轮的原库报告和 summary.json；该目录被 Git 忽略，以免实际任务内容意外进入研究仓库。

## 正式业务验证应增加的步骤

1. **固定候选项**：记录 Skill 版本、模型版本、服务入口、推理参数及评分标准。
2. **准备代表性样本**：在六个演示任务之外，加入真实脱敏任务、边界条件、容易混淆和应拒绝的情况。样本量由任务差异和所需精度决定。
3. **建立人工参考**：让业务负责人对一批输出独立评分；检查 AI 裁判的误判，尤其是“错误输出被判通过”。
4. **保持输入公平**：只改变 Skill；任务数据、可用工具、预算和执行环境保持一致。
5. **重复并控制顺序**：原库固定先运行 with_skill，再运行 without_skill；正式实验应通过独立调度或适配进行随机/交错顺序，控制服务时段影响。
6. **分开量化**：报告检查条件通过率、完整任务成功率、关键错误率、目标与裁判的耗时和费用。不能用一个分数替代所有指标。
7. **报告不确定性**：对同任务做配对比较；如重复多轮，分析时注意同一任务内结果相关，不能把重复样本全当独立业务任务。
8. **设置发布门槛**：样本非空、调用无异常、关键规则不失败，再考虑平均增益；必要时人工复核所有关键失败。

## 结果如何解读？

- 两组都很好：可能模型本来就会，也可能样本太简单。
- 有 Skill 更好：在输入公平且裁判校准后，才有理由归因于 Skill；仍需要说明样本范围。
- 有 Skill 更差：检查指令冲突、过度约束、上下文增长，以及 Skill 是否引导了错误步骤。
- 分数波动大：先看生成随机性和裁判一致性，不能仅根据一次结果改写结论。

本项目的可选脚本会保存每轮结果并计算差值均值，但**没有自动完成人工校准、随机顺序或显著性分析**。完成运行后，仍需按上述流程解释数据。
