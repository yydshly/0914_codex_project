# 效果分析与实验记录

## 证据范围

本研究有两类实际运行证据：

- 上游的 15 项测试通过，含本地模拟 HTTP 接口上的 CLI 集成测试。
- 外部研究脚本的 12 项机制观测全部复现，直接调用未修改的上游编译产物。

**没有使用真实大模型。本页的 0%、100% 等数值来自确定性模拟响应，只用于分离输入、评分与统计逻辑的影响。** 它们不能说明某个商业模型的质量、平均准确率或某个业务 Skill 的实际增益。

实验程序：[experiments.mjs](../src/experiments.mjs)。实际结果：[experiment-results.json](../artifacts/experiment-results.json)。

## 实验结果

| 编号 | 方法 | 实际观测 | 解释与建议 |
| --- | --- | --- | --- |
| E01 | 模拟目标忽略 Skill，只读 CSV；使用普通附件配置 | 有 Skill 100%，无 Skill 0%，差值 100 个百分点 | 附件不对称足以制造全部差值。不能归因于 Skill 内容 |
| E02 | 使用相同目标，将同份 CSV 写入两组相同的 prompt | 两组均为 100%，差值 0 | 控制任务数据后，前一实验的差值消失 |
| E03 | 对同一次工具调用设置 4 条应通过和 1 条应失败的规则 | 4/5 通过，裁判调用 0 次 | 工具检查是可预测的本地判断，能减少裁判开销 |
| E04 | 裁判连续返回不可解析文本 | 调用 2 次，条件失败 | 对格式错误有有限重试，最终按失败处理 |
| E05 | 模拟裁判返回 passed=true，没有 evidence | 仍通过，显示“judge did not provide concrete evidence” | 提示词要求证据不等于程序强制检查证据 |
| E06 | 用例没有任何评分条件，目标返回 error | 输出含 ERROR；passed=0、failed=0、total=0、pass_rate=1 | 空检查可显示 100%，运行错误未独立成为失败条件 |
| E07 | 裁判交换 A、B 两条结果的顺序 | B 的 PASS 和证据被绑定到 A | 结果按位置归一化，未用 ID 或条件文本校验对应关系 |
| E08 | 原任务和 expected_output 各放唯一标记，同时提供 assertions | 裁判看见模型输出，没看见原任务或预期答案标记 | “回答是否正确”这种模糊条件可能缺少评判依据 |
| E09 | 不提供 assertions，只提供 expected_output | 自动产生 1 条评分条件 | 最小预期输出路径可以工作 |
| E10 | 本地兼容接口返回一个 lookup 工具请求 | HTTP 请求 1 次、工具调用记录 1 条、工具结果消息 0 条、最终文本为空、断言通过 | 验证的是请求被提出，不是工具成功执行 |
| E11 | 一个用例 1 条全部通过，另一个用例 9 条全部失败 | benchmark 均值 50%，整体断言通过率 10% | 统计权重不同；读报告前先统一“通过率”的定义 |
| E12 | CLI 指向没有任何 Skill 的空目录 | skills=0、failed=0、退出码 0 | 目录写错或筛选为空，自动化也可能误报成功 |

## 最关键的对照实验

E01 的模拟目标写死了这样的行为：

```text
如果 user 消息包含 February,18 → 输出 February: 18
否则 → 输出 No task data
完全不读取 system 消息或 Skill 正文
```

Skill 内容故意与数据分析无关。即便如此，报告仍显示实验组 100%、基线组 0%。E02 只改变数据放置方式，使两组都得到相同 CSV，分差即变为 0。

这足以证明：**当前实现中的附件可用性是一个混杂因素，报告差值未必是技能本身造成的。** 这不证明所有 Skill 都没有用，也不估计真实模型受影响的幅度。

直接查看[原库生成的报告](../artifacts/mechanism-demo.html)和[benchmark](../artifacts/attachment-benchmark.json)。报告标题与目标/裁判名称都标明了模拟性质。

## 对“实际效果”的判断

### 可以肯定的部分

- 流程确实可以跑通：用例加载、两组调用、评分、记录和 HTML 报告生成。
- 明确、可程序判断的工具规则适合纳入自动检查。
- 输出和评分记录能帮助定位失败，优于只存一个总分。

### 本次无法给出的结论

- 没有测得任何真实模型的 Skill 提升百分点。
- 没有测得 AI 裁判与人工验收的一致率。
- 没有做真实浏览器、文件生成、业务 API 或脚本执行测试。
- 没有验证多 Skill 路由和长任务规划能力。

上游自带测试和本研究实验主要验证软件行为。“测试都通过”与“它生成的所有评测结论都可靠”是不同的问题。

## 若用于实际项目，建议先做什么？

| 优先级 | 改进 | 对应证据 |
| --- | --- | --- |
| 高 | 两组共享相同任务数据，只改变 Skill 上下文 | E01/E02 |
| 高 | 用例数量必须大于零，每条用例必须有有效评分条件；目标调用错误单独计失败 | E06/E12 |
| 高 | 将原始任务、必要输入和预期答案明确交给裁判；条件采用稳定 ID | E07/E08 |
| 中 | 缺少证据或格式不完整时标记为“无法判定”，避免静默计 PASS | E05 |
| 中 | 将业务完成验证与工具请求检查分开，接入实际执行环境 | E10 |
| 中 | 报告标明统计分母，分别显示用例均值与整体断言通过率 | E11 |
| 中 | 保存裁判调用耗时、Token、原始响应和人工复核结果 | 源码分析 |

这些是建议，**没有修改本项目的上游副本**。两组固定先后顺序、模型输出随机性和裁判偏差需要在正式试验设计中另外处理。
