# 002 · Agent Skills Eval：Skill 能力校验引擎

**agent-skills-eval 读取已经编写好的 Skill、测试任务与评分标准，自动调用模型执行任务、逐条评分，并对比加载与不加载 Skill 的效果。** 它帮助发现技能是否达标、改动是否引入退步，把一部分人工验收转为可重复的自动检查。

可以将它作为“校验能力 Skill”的底层评测引擎：由 Skill 说明校验流程，调用这个库运行测试，再汇总结果供人复核。**上游仓库提供的是评测程序；这是一种可封装方式，本研究没有另行实现完整的校验 Skill。**

## 核心能力

| 能力 | 输入与输出 | 实际价值 |
| --- | --- | --- |
| 自动运行测试 | 输入 Skill、测试任务与指定模型，取得模型回答 | 批量验证已定义的技能要求 |
| 有 / 无 Skill 对照 | 开启基线对照，分别运行两组并汇总差值 | 分析 Skill 是否带来额外收益 |
| 语义条件评分 | 裁判模型按预设标准判断通过或失败 | 自动检查回答是否满足内容要求 |
| 工具调用检查 | 程序检查工具名称、参数和次数 | 精确核对模型提出的工具请求 |
| 结果与证据报告 | 保存回答、逐条判断、耗时与 Token，生成 HTML/JSON 报告 | 定位失败项，供人工复核与后续比较 |
| 重复验证 | 修改 Skill 后再次运行相同测试集 | 发现退步，支持持续改进 |

适用对象包括客服回复、内容写作、数据分析和代码审查，不限于代码测试。工具请求正确不等于工具执行成功，完整业务结果需要另外验证。

## 从需求到验证：责任如何划分？

1. **用户确定能力范围**：明确要完成什么、不承担什么，例如只给退款建议，不直接转账。
2. **用户或 AI 梳理场景、设计测试**：覆盖正常、异常和边界情况，起草任务、输入和通过条件。
3. **用户确认标准，用户或 AI 编写 Skill**：Skill 告诉模型怎么做；测试检查模型有没有做到。两者可以交替完善。
4. **这个库自动验证**：读取准备好的内容，调用目标模型、评分并生成报告。
5. **人工复核与迭代**：判断问题来自 Skill、测试还是裁判，修改后再次运行。

库不内置需求分析、场景生成、测试设计或自动改写 Skill。前期可以借助其他 AI 工具完成，但不能把这些协作步骤当成库的现成功能。

**退款示例：**测试题不提供收货日期，评分标准要求先追问；如果回答直接认定“可以退款”，就应检查出不符合标准。这验证的是指定情境中的行为，不等于证明所有退款任务都能正确处理。

## 它解决什么问题？

过去：人写 Skill → AI 执行 → 人逐条验收。

这个库：人写 Skill、测试任务和检查标准 → 模型执行 → AI 裁判或程序检查 → 生成报告 → 人抽查、修订标准。

它本身是 TypeScript 评测工具，不是另一份负责验收的 Skill，也不限于代码任务。文本写作、客服、数据分析和工具参数选择都可以作为测试对象。

## 本次最重要的发现

| 发现 | 实测证据 | 对使用者的影响 |
| --- | --- | --- |
| 对照组缺少任务附件 | 忽略 Skill 的模拟执行器也得到了 100% 对 0%；两组数据相同后变成 100% 对 100% | 附件任务的分数差异混入了“是否有数据”的影响 |
| 裁判的证据要求缺少程序强制校验 | passed=true 且证据缺失仍计通过 | 不能认为报告中的 PASS 都有充分证据 |
| 无检查条件也会给通过率 | 目标调用报错，0 条检查仍显示通过率 1 | 必须增加用例数量、评分条件和运行错误检查 |
| 工具调用只是请求记录 | 本地模拟接口收到 1 次请求，没有工具结果回传，工具断言仍通过 | 不能据此证明工具执行成功或任务完成 |
| 评分信息可能不足 | 有 assertions 时，原始任务与 expected_output 不自动进入裁判提示词 | 检查条件应包含必要事实，或者扩展裁判输入 |

以上均是固定版本上已复现的程序行为；**模拟分数不是某个真实大模型的能力分数**。完整证据见[实验记录](notes/02-findings.md)。

## 快速复现

从总仓库根目录进入本项目后运行：

```powershell
cd projects/002-agent-skills-eval
npm run setup
npm run check
```

需要 Node.js 20 或更新版本（本研究要求；上游声明为 Node.js ≥18）、npm，以及首次安装依赖时的网络连接。源码已保存在本项目，无需重新下载仓库。安装阶段使用锁文件并禁用安装脚本；随后显式构建和运行测试。

`check` 依次执行：

1. 校验 26 份上游文件的 SHA-256，与下载记录一致。
2. 构建上游库并运行其 15 项测试。
3. 执行 12 项研究实验，生成 JSON 结果和上游 HTML 报告。

预期看到 15 项上游测试通过，以及 `12/12 mechanism observations verified`。后者表示程序行为成功复现，**其中多项复现的是评测缺陷，不是“12 项业务能力全部通过”**。

运行输出：

- `artifacts/experiment-results.json`：最新一次观测。
- `artifacts/mechanism-demo.html`：附件不对称示例报告。
- `artifacts/attachment-benchmark.json`：该示例原始统计。
- `artifacts/runs/`：每次实验的独立目录，保留全部中间记录，Git 忽略。

如需保存新的上游测试日志：`npm run test:upstream > artifacts/upstream-tests.txt`。当前保存的日志来自本次实际运行。

## 如何评价它的效果？

- **流程自动化有效**：加载、调用、评分、产物落盘和报告生成均已跑通。
- **适合检查已定义的行为**：工具名、参数、明确输出条件比较适合自动验收。
- **评测可信度需要补强**：对照输入、裁判上下文、证据校验和空测试处理影响结果解释。
- **真实质量提升尚无本项目数据**：已准备 6 个退款审核任务、12 条自包含标准和可选运行器；实际提升幅度需要指定模型后运行，并用人工评分校准。

建议先修正两组输入不对称，增加“没有测试则失败”的检查，再用于发布门槛。把模型的文本和工具选择作为评测边界；浏览器操作、脚本执行、文件正确性和业务副作用需要额外运行环境。
