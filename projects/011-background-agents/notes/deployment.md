# 部署条件与最小试用路线

本页整理固定版本文档及代码要求；本次未部署外部服务。依据：[S10](sources.md#s10)、[S11](sources.md#s11)、[S19](sources.md#s19)、[S21](sources.md#s21)。

## 实际需要准备什么

| 组件 | 用途 | 需要准备 |
| --- | --- | --- |
| Web 界面 | 选择仓库、发任务、看结果 | Next.js 服务及正确的控制服务地址 |
| 控制服务 | 存任务、管理认证、调度与实时通信 | Cloudflare 部署，或 Node 容器与持久存储 |
| 代码仓库接入 | 拉取代码、推分支、创建 PR | GitHub App 安装与对应权限；登录提供商配置 |
| 模型接入 | 推理与编程决策 | 与运行层兼容的模型认证方式 |
| 沙箱后端 | 真正执行代码和命令 | 选择受支持后端并配置运行镜像、密钥等 |
| 项目环境 | 正常构建与测试 | 依赖、必要的测试凭据、setup/start 脚本 |
| 连通性 | 沙箱回连控制服务 | 沙箱能够访问的 HTTP/WebSocket 地址 |

根 `package.json` 声明 Node.js `>=22.13.0`，按该要求准备，不采用较旧指南中的宽松最低版本。不同 Python/基础设施工具要求按实际选择的后端确认。

## 两条控制服务部署路线

1. **Cloudflare 路线**：使用官方部署指南中的 Workers、Durable Objects、D1 等组件，配置 Web、GitHub 和沙箱。集成机器人按需要逐个加入。
2. **容器路线**：按 `CONTROL_PLANE_CONTAINER.md` 配置 Node 控制服务、SQLite 卷和兼容 S3 的对象存储。仓库 Compose 栈包含控制服务及配套存储/备份组件，**不包含 Web 应用**。Web 需另外启动；沙箱仍需另行接入。

如果控制服务放在本机而沙箱在远端，只配置 `localhost` 无法让远端回连，需要可达地址。容器方案的持久恢复依赖单实例访问数据目录，不能直接套用多副本负载均衡。

## 建议的最小试用顺序

以下是后续可执行路线，未声称已完成。

1. 准备一个小型测试仓库，包含确定能在 Linux 环境运行的测试命令。
2. 选择一个模型运行层和一个沙箱后端，先跑通网页到控制服务的登录与会话创建。
3. 确认代理实际进入沙箱，能够获取仓库并执行既有测试。
4. 派一个可确定验收的小任务，例如修复带现成失败测试的日期格式化错误。
5. 要求交付差异、测试结果、独立分支和 PR，人工检查未扩大改动范围。
6. 再验证关闭网页、后续指令、环境恢复。单任务链路稳定后再验证子代理和自动触发。

控制服务健康检查成功，只证明服务启动；网页能打开，只证明入口可访问；必须看到真实文件改动、命令结果和 PR 才能证明完整链路跑通。

## 成本怎样记录

不在此估算金额。试用时分别记录模型消耗、沙箱活跃时间、镜像/快照与存储、控制服务及对象存储资源，以及人用于配置、审核与返工的时间。

比较“人工使用已有编程助手”与“后台平台执行同一任务”时，应保持模型、仓库版本、需求和验收标准一致。任务并行可能降低总等待时间，也会增加同时使用的计算资源；两项需要分开观察。
