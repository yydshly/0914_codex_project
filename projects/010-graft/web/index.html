context/build.ts ↗

    
进一步理解：自然语言查询，为什么不一定需要向量数据库？＋
这个版本的查询把任务词项与符号名、签名、说明等内容进行匹配，再结合图结构排序。源码包含 IDF 词项权重、代码体 BM25 评分和 Personalized PageRank 图排序；关系查询还可以直接沿边查找。
这些是确定性的检索方法，不等于一个理解任何自然语言的模型。问题措辞、标识符、说明质量和语言覆盖都会影响命中效果。按路径缩小范围、返回不同文件的代表位置，也能减少结果被单个文件占满。

03 / KEEP IT CURRENT
代码变了，地图怎么办？

    
查询前先检查变化，构建时复用没有变动的解析结果。结构更新和模型摘要更新是两件事。
此处只切换说明，不修改文件或运行 Graft。
结构图谱
深度摘要

    
缓存为什么快，又有哪些边界？＋
查询的轻量检查使用文件大小、修改时间等指纹；需要重建时，构建过程读取并计算内容哈希，未变化文件复用解析缓存。因此“少做解析”不等于“重建时不读文件”。
保持相同大小与修改时间的特殊改写可能绕过快速检查；哈希检查模式可以避开这一盲点。刷新失败时存在返回旧图谱并附提示的降级路径。不能把自动刷新等同于信息永远准确。

04 / THE DIFFERENCE
Graft 与 Caveman：两种减少输入的方式

    
GRAFT / 先找对位置
“这次应该读哪些代码？”
整个项目→相关位置
＋依赖关系→上下文
从任务出发，查找相关节点，组织片段与关系。类似先找到书中相关章节及其引用。
CAVEMAN / 精简选中的材料
“这些材料怎样更精简？”
已取回内容→按内容类型
精简与保留→上下文
处理已选中的代码、日志等输入，提供原文恢复与回退。类似将拿到的章节整理成精简材料。

    
这是侧重点的区别：Graft 的接口轮廓与片段输出也会精简内容。两者能力有重合，组合使用的净收益需要实测。
