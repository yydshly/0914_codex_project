# MiroFish 理解汇总：能力、原理、场景与展示效果

研究对象为 [666ghj/MiroFish](https://github.com/666ghj/MiroFish)，固定版本 `39d849138ef254f6c737ab4c4705e5545dbe31d4`，查阅日期 2026-09-16。本记录依据源码与公开案例说明；本项目没有运行模型、Zep 或 OASIS 完整链路。

## 能力摘要

MiroFish 将“背景资料 + 假设问题”转化为多个具有身份与上下文的模拟角色，让角色在虚拟社交环境里观察、决策、行动，再对互动记录进行分析。用户最终得到可检查的角色与关系、动作记录、报告，以及可继续追问的角色和报告智能体。

知识图谱解决背景中的关联与检索问题；大模型负责生成和判断；OASIS 负责虚拟环境与动作执行；MiroFish 编排流程并提供操作界面。它是多智能体社会模拟应用，不是单独的知识库问答工具，也不是仅靠一份提示词实现的技能。

## 输入：材料、问题与情境约束

| 输入 | 内容示例 | 作用 |
| --- | --- | --- |
| 背景资料 | 事件时间线、公开评论、产品方案、客户访谈、小说章节、人物小传 | 为实体关系、角色设定和判断提供依据 |
| 自然语言问题 | 发布这份公告后，各方可能怎样反应？秘密公开后，人物会怎样选择？ | 指定要探索的假设与观察目标 |
| 写入资料或需求的约束 | 时间点、各方利益、已知事实、角色掌握的信息 | 尽量约束模型补全，避免与背景冲突 |

固定版本文件解析器支持 PDF、TXT、Markdown（`.md` / `.markdown`）。PDF 路径提取文本，不能据此宣称内置扫描件 OCR。表格、音视频、数据库或链接内容需要先准备成支持的文本材料，不能把任意数据接入当成已核实功能。

仅提供一个话题，会让角色背景与行为更多依赖模型补全。若希望模拟具体人群，应提供真实分层、约束和历史反馈，并检查生成的人设是否遗漏或失真。

## 内部原理：角色与模型怎样结合

1. **解析与构图**：提取材料文本，经 Zep 组织实体、关系和可检索背景。
2. **生成角色与环境**：模型结合实体资料生成简介、详细人设等，另生成活动、时间、初始帖子等配置。人设进入模型提示与上下文；并非为每个角色训练新模型。
3. **调度互动**：程序依据模拟轮次和活动设置选出参与者。角色根据当前上下文让模型选择行动，再交给 OASIS 执行。
4. **保存并继续**：环境保存帖子和动作结果，相关信息与记忆更新，影响后续角色可观察到的内容。并非所有角色都同时行动或共享全部信息。
5. **分析与追问**：ReportAgent 检索模拟信息、调用工具或采访角色，生成报告；模拟后仍可进行角色采访和报告对话。

```text
角色档案 + 当前可见信息
          ↓
       大模型决策
          ↓
OASIS 执行动作 → 环境 / 记录更新
          ↑             ↓
          └── 下一轮观察 ┘

模拟记录 → 报告分析与后续问答
```

多个 Agent 可以共用同一个模型配置：差别主要来自人设、上下文和可用动作。不同角色的回复可能仍共享同一模型的偏差，角色数量不能自动带来独立判断。

OASIS 是独立的仿真引擎，提供 Twitter / Reddit 风格的虚拟社交环境。角色可以发帖、评论、转发等，具体动作取决于平台；它不会因此在真实社交账号上发布内容。它也不是默认具备物理世界、财务交易、完整剧情或狼人杀胜负规则的通用游戏引擎。

报告模型主要事后整理与解释；通常推动下一轮的是角色行动和环境变化，不能把整个架构理解成“汇总模型写下一段剧情，其他角色照着演”。

## 场景：官方案例与可设计用途

| 场景 | 典型问题 | 可以探索的产出 | 依据与边界 |
| --- | --- | --- | --- |
| 舆情与公关 | 一份回应会引出哪些质疑？ | 分歧、误解、转述变化与沟通缺口 | 官方有武汉大学舆情推演示例，输入来自 BettaFish 的分析报告；不等于 MiroFish 自带全网监测 |
| 故事后续推演 | 人物在新信息下会怎样选择？ | 动机冲突、可能反应与情节方向 | 官方有《红楼梦》前 80 回推演示例；不等于考证出失传原文，也不保证直接生成连贯的成稿小说 |
| 市场调研辅助 | 各类客户为什么接受或拒绝？ | 顾虑、需求假设、真人访谈提纲 | 可基于机制设计；模拟访谈不是实际客户证词、抽样统计或销量预测 |
| 产品与定价评审 | 改价或取消功能会影响谁？ | 潜在反对理由、规则理解缺口与改进线索 | 可分别运行候选方案；对照实验需要控制材料、模型、预算等，不宣称内置完整 A/B 评测 |
| 规则与政策讨论 | 新规则下各方可能怎样应对？ | 利益冲突、适应行为和执行疑问 | 可设计用途；现实执行效果仍须外部证据验证 |

这些用途共用同一套社会模拟机制，不是五个已经独立验证的专业预测模型。

## 呈现：图谱只是其中一种

| 原版呈现方式 | 用户看到什么 | 用途 |
| --- | --- | --- |
| 关系图谱 | 人物、组织、事件等实体及关联 | 理解背景；关联不代表因果 |
| 角色档案 | 简介、人设与配置 | 检查模拟参与者的设定 |
| 互动记录 | 按时间或轮次记录的发帖、评论、转发等动作 | 追踪讨论与核对过程 |
| 运行状态 | 模拟进度、平台状态、动作数量 | 判断运行情况；不是预测准确率 |
| 分析报告 | 按章节组织的文字分析、模拟观察和结论 | 阅读推演结果并核查依据 |
| 深度互动 | 与角色聊天、向报告智能体提问 | 追问立场、疑问与报告依据 |

因此，原版不是主要靠一张图输出答案。图组织背景，记录展现发生了什么，报告提供分析，对话用于进一步追问。

## 价值：发现遗漏，比“演得像”更重要

本项目使用 Unity 2023—2024 收费变更的公开事实解释价值：如果团队只关注费用，模拟是否能提示“长期规则和信任”问题，并帮助改进方案？这属于研究者设计的实验，没有证据表明 Unity 使用过 MiroFish。

有效的新增价值应来自此前遗漏、后来被真实客户或事实验证的顾虑。如果模拟只是重述公开文章中已经存在的问题，直接读材料或单次模型分析可能已经足够。比较时应在预算可比的条件下，评估新增有效问题、无证据结论、建议可执行性、时间和费用。

历史案例还存在模型已知结局的风险。即使不上传后来发生的事件，模型也可能在训练中见过。模拟中反复出现某种结果，也不能未经校准就解读成现实发生概率。

## 本项目实际交付与未验证范围

- **已交付**：能力全景图和流程图（PNG / SVG）、中文交互教学页、三个原创场景、两种预设分支、四轮事件回放、对话与信息流图、角色预设访谈、报告下载、原版截图与来源链接。
- **真实案例材料**：Unity 历史来源、截至指定日期的资料摘要和候选方案实验设计；历史事实与模拟假设明确分开。
- **网页检查**：记录见 [validation.md](validation.md)，包括交互检查、下载、键盘操作、响应式显示、图像与构建检查。
- **没有执行**：原版后端启动、真实模型 / Zep / OASIS 推演、预测回测、真人代表性验证、运行成本或大规模性能测量。

教学页的聊天记录不是实时 AI 回复，信息流箭头是作者明确编写的引用关系；故事中的私人想法有单独标记，不作为其他角色已知的信息。它们用于说明机制，不能冒充原版界面或实际运行结果。
