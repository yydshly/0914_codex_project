MiroFish 可以用于组织一次发布前的反对意见演练。输入当时的公开方案与反馈，让不同角色互动，再检查每项应对措施是否回答了他们的问题。以下是基于案例设计的实验，不是 Unity 使用过 MiroFish 的记录。

01 · 给什么资料

当天及之前的方案、公开反馈；补充真实客户分层、使用习惯与历史承诺。2024 年的取消公告留作事后参照。

02 · 让谁参与

长期工作室、独立开发者、发行商、技术传播者和官方解释者。身份与约束应有资料依据。

03 · 追踪什么

哪些顾虑持续出现？谁的回应改变了其他角色？解释清楚后，是否仍有人担心未来规则改变？

04 · 带走什么

未解决的问题清单、具体触发条款、可追溯的互动记录，以及必须向真人核实的判断。

真正值得付费的产出

把一项遗漏的顾虑，变成发布前的一次修正。

例如：如果模拟反复出现“即使现在更便宜，也担心以后再改规则”，就应把长期条款、版本保障和变更沟通机制列入真人访谈与方案评审，而不只继续打磨降价公告。

但这个案例也提出一个反问

真实开发者已经公开说出了“信任”问题。若 MiroFish 只是重述这句话，直接阅读资料或让单模型分析就可能足够。它必须多发现可验证的遗漏，或帮助比较应对方案，才有额外价值。

怎样证明这个库真的帮到了决策？

把同一批资料分别交给“单模型直接分析”和“MiroFish 多角色互动”，在预算可比的条件下，让不了解生成方式的业务评审比较：新增了多少有效问题、多少结论无证据、建议能否改进方案、耗时和费用是多少。最后用真实客户访谈验证新增问题。

这个历史案例有明显的事后信息风险：即使不上传 2024 年公告，当前模型也可能已知道结局。因此它适合说明价值，不足以证明预测能力。更可信的验证应使用尚未公开的新方案，先保存预测，再等待真人反馈。

真实发生的取消事件也不能证明某一项顾虑单独导致了最终决策，更不能证明 MiroFish 当时一定能预测到。

如何从这个展示，走到一次真实运行？

固定上游版本，准备 Python 3.11–3.12、Node.js 和 uv；配置兼容的大模型 API 与 Zep Cloud，再安装并启动原版前后端。具体依赖以固定版本文件为准。

使用一份可公开的背景资料和一个明确问题，从少量角色、少量轮次开始。保存输入、模型、参数、动作日志与报告。先检查机制，再用真实历史事件做回测。

模型调用会产生成本；官方建议先尝试少于 40 轮。真正的对照实验还需要控制模型、资料、预算与随机性，并与单模型分析和真实结果比较。

为什么不能把它当成“未来计算器”？

角色、初始帖子、活动设置和输入资料都会影响走向。同一个模型生成很多角色，仍可能共享偏差。代码还会生成 narrative_direction（叙事 / 舆论方向）字段；字段存在不等于已证明它如何影响全部结果，需要实验核对。

虚构访谈适合帮助设计真实调研问题，不能作为真实用户证词。多次模拟中出现的频率，也不能未经校准就解释成现实发生概率。
