# 蜂群的价值与能力范围

2026-09-16 核对官方文档。以下是平台描述与独立研究解读；没有新增云端实测。

## 技能沉淀只是其中一层

“每个工种积累技能”可以作为产品设计思路，但不能从岗位名称推导出技能已经可靠，也不能推导出每个岗位必须拥有独立知识库。经验可以围绕任务、领域和适用条件组织，由不同角色复用。

我们用三个层次理解沉淀：

| 层次 | 要回答的问题 | 说明性例子（非业务实测） |
| --- | --- | --- |
| 方法与案例 | 这件事怎么做？ | 接口接入步骤、失败条件与验收记录 |
| 协作流程 | 多个人怎么衔接？ | 研究→实现→审查的输入输出约定 |
| 组织反馈 | 下次怎样组织更合适？ | 配合记录、流程质量与耗时 |

方法资产对应 [GEP](https://evomap.ai/zh/wiki/16-gep-protocol) 的策略、案例和事件；后两层对应 [蜂群文档](https://evomap.ai/zh/wiki/10-swarm) 描述的流水线模板、协作历史与编排结果。三层划分是我们的解释框架，不是官方分类。

## 平台能力清单

| 能力 | 官方描述的机制 | 我们的用途解读 |
| --- | --- | --- |
| 任务组织 | 拆解、依赖协调与聚合 | 独立部分并行，依赖部分按顺序推进 |
| 找人与组队 | 能力目录、匹配与 Worker 池 | 找到适合任务且可用的执行者 |
| 求解模式 | 分工、发散收敛、审议、流水线 | 根据问题选择合作方式 |
| 通信与交接 | 对话、共享工作区、事件通知 | 交换约定、产物与状态 |
| 审查返工 | PDRI 循环 | 把验收纳入过程，不能只看提交状态 |
| 失败恢复 | 超时与候补改派 | 执行者失效后仍有恢复路径 |
| 知识与流程复用 | 共享记忆、订阅、模板 | 减少重复组织与查找工作 |
| 组织反馈 | 协同记录与编排策略选择 | 为后续选人与选流程提供依据 |
| 运行控制 | 预算、并发、组织策略 | 约束自动执行的资源范围 |
| 网络参与 | 认领、贡献与结算 | 提供跨执行者参与机制 |

来源：[蜂群 Wiki](https://evomap.ai/zh/wiki/10-swarm)、[2026-04-06 蜂群更新说明](https://evomap.ai/zh/blog/swarm-privacy-computing)。后者还描述隐私计算扩展；本研究未审计，不据此宣称已验证其机密性或隔离保证。

## 客户端与平台不能混为一谈

- EvoMap Hub：网络侧的组织、调度与共享服务。
- Evolver：执行侧经验流程、提示与网络接入客户端。
- 模型与执行宿主：理解任务并实际调用工具。

固定版本 [README](https://github.com/EvoMap/evolver/blob/31b0691acd97ba18878019312e646f1f2d970d43/README.zh-CN.md) 描述客户端 Worker 模式，且本地开关与网页端配置承担不同职责。本研究未启用接单或运行云端任务；只阅读相关说明。

## 证据与版本差异

1. 既有 77 项通过测试覆盖本地选择器、哈希与提示词；不证明云端协作可交付或节省成本。
2. 官方蜂群调度文档明确描述能力向量匹配。它是“选择参与者”的机制，不能直接证明本地 Gene 选择或所有经验检索都采用向量 RAG。
3. 更新博客给出审查阈值 60，当前 Wiki 的 PDRI 段落给出 70；返工轮次在不同段落也有差异。网页仅介绍机制，不承诺统一默认配置。
4. Wiki 事件段落说 webhook 已废弃，Worker 段落仍描述 webhook 推送。接入方式需按实际版本核对，不把混合年代的段落当作一致协议。
5. “改善编排”是官方功能描述；“最优策略”“群体更聪明”需要额外效果证据。实际评估应记录成功率、质量、总成本、耗时、返工与人工干预。
