从经验复用，
走向群体智能

是的，EvoMap 可以理解为探索群体超级智能的一种工程方案。它尝试让 AI 保存经验、相互借鉴、分工协作，逐步提高整个系统的能力。

我们的理解：以群体智能为愿景，探索类似 RAG 的经验检索与沉淀，让多个 Agent 复用方法，并用执行反馈继续改进。这是一个具有参考价值的产品方向，整体收益和更远的超级智能目标仍需验证。

02

它押注的，是经验能在 AI 之间积累

一次有用的尝试，成为下一次工作的起点。

发现问题从任务和错误中识别需求
→
借鉴经验寻找适用的方法与案例
→
执行验证在当前环境中真正试过
→
保存反馈留下有效方法与失败条件
沿着时间积累

AI 之间留下“维修手册”

A 今天解决了问题，B 明天遇到类似问题时可以参考。它们无需同时在线、也无需一起执行。

这叫经验复用。
在同一任务中协作

AI 之间分配不同工作

A 分析、B 实现、C 检查，再把结果合并。需要协调分工、处理冲突，并验证最后的交付。

这叫多智能体协作。
两者可以结合，但不是同一件事。

分享了很多经验，不等于已经形成超级智能；增加 Agent 数量，也不保证结果更正确。关键是能否在真实任务中保持质量、减少无效工作。

类似 RAG，检索的是“怎样做事”的经验

RAG 的基本思路是先查找相关资料，再把资料交给模型使用。这里也有类似过程：从任务与错误中提取线索，选择相关策略与案例，加入执行提示，让 Agent 结合当前环境做事。

检索增强的共同点

把外部记忆带进当前任务

常见文档 RAG 查找知识片段；这里侧重做法、适用条件、历史案例和验证记录。二者都可以帮助模型借鉴已有信息。

这条路线继续探索什么

把执行结果带回经验库

执行、验证、记录成败，供后续任务和其他 Agent 再次选择。带记忆与反馈的 Agent 系统也能这样设计，并非 EvoMap 独有。

“类似 RAG”是机制类比，不是对底层技术的断言。已验证的是原版策略选择与案例匹配，不能据此认定平台使用向量数据库或某种向量检索。存成文件、JSON 或数据库只是存储选择；关键在于适用性判断、结果验证与反馈质量。

看起来像定制规则：规则和经验各起什么作用？

规则规定资产格式、使用条件、执行约束和验收办法；经验记录某种方法在什么环境下成功或失败。模型和工具负责执行，验证结果再影响后续选择。因此“配置规则”是其中一部分，持续积累可验证的经验才是我们关注的产品方向。

一个可落地的起点：技能 ＋ 本地经验库 ＋ 检索 ＋ 执行验证 ＋ 反馈回写。

先让一个 Agent 在后续任务里复用，再扩展到多个 Agent 共享。数据库本身不会产生群体智能；是否提高整体能力，需要对照实验。这是我们的产品化建议，不是对官方部署架构的复刻。

03

蜂群：按需组队，再让经验留下来

能力决定能做什么，角色决定这次负责什么，经验帮助它做得更好。

一句话记住：当下能协作，以后有经验可复用。

“动态组队”就是按任务找合适的 AI；“通信”就是交接方案和问题；“审查返工”就是没做好再改；“失败改派”就是执行者失效后尝试换人；“共享记忆”就是留下可参考的工作手册；“预算控制”就是限制资源开销。

蜂群的价值可以分成两部分：这一次，把多个执行者组织成可验收的交付；下一次，让方法、流程和协作记录有机会减少重复摸索。这些是目标与机制，实际收益还要测量。下方详细内容解释它与普通多 Agent 协作的关系及能力边界。

在 EvoMap 语境里，蜂群属于多 Agent 协作的一种组织方式。多 Agent 协作是总称；蜂群强调围绕目标组织参与者、协调执行、审查和迭代。成熟的多 Agent 系统也能具备这些能力，不能只凭名称判断先进程度。

每个工种积累技能，是其中一部分价值。

更完整的理解是：既复用“怎么做事”的方法，也改进“怎样组织大家做事”。经验可以按任务、领域、条件组织并跨角色复用，不必给每个固定工种分配一个独立知识库；有了角色名称，也不代表它已经具备可靠技能。

方法沉淀

这件事怎样做

例如接口接入步骤、部署条件、失败原因和验证方法。供执行者按需参考。

流程沉淀

几个人怎样配合

例如把“研究 → 实现 → 审查”的交接流程保存为模板，用于后续任务。

协作记录

以后怎样组织更合适

记录团队配合和编排结果，为后续选人、选择协作方式提供依据。

这是我们的三层归纳。方法资产依据 GEP 文档；流水线模板、协作历史与编排反馈依据 蜂群文档。这些记录不等于模型权重自动训练，也不保证每次都能选对。

“给一批 Agent 能力，再按需赋能”，要分开看

先选谁来做

按已有能力匹配

例如网页实现需要编程工具，部署需要对应环境与权限。选人时要考虑它实际能做什么、当前是否可用。

再提供怎样做

补充技能与经验

提供页面规范、部署步骤、历史失败案例和当前任务上下文。这些能指导执行，但不会自动授予工具、权限或保证成功。

能力

能做什么

模型、工具、环境和权限共同构成执行条件。

角色

这次负责什么

任务中的岗位，不必是永久身份；同一 Agent 可以在不同任务承担不同职责。

经验

如何做得更好

方法、条件、案例与成败依据，需要在当前任务重新验证。

“蜂后、工蜂、不同工种”怎样对应？

协调者

理解目标、拆任务、组织参与者、跟踪进度。

执行者

负责研究、实现或测试，交出具体结果。

审查者

核对证据和验收标准，必要时提出返工。

汇总者

处理结果衔接与冲突，整合最终交付。

可以把“蜂后”当作软件协调者的比喻；这里只讨论任务岗位，不把它当成生物蜂群机制的复刻。工种可以预设，也可以按任务安排；“等上层派单”是一条路径，Agent 主动认领任务也是一条路径。

一定要有一个固定的“蜂后”吗？

这个概念并不要求一个永久中央角色。本图展示的是方便理解的协调流程；具体系统可以由平台、规划 Agent 或任务发起者承担协调。EvoMap 文档同时描述了任务认领、平台调度、并行分工、独立探索、审议和流水线等方式。

官方介绍的蜂群，具体提供哪些能力？

以下是官方平台能力描述，尚未由本研究进行云端实测。每张卡片同时给出我们的用途解读，便于理解这些机制解决什么问题。

01 · 规划与分工

拆任务，按依赖推进

文档描述任务拆解、并行求解与依赖协调。

用途解读：独立工作同时做，依赖接口结果的工作等前置完成。

02 · 按需找人

能力目录与动态组队

结合能力、信誉、可用性等信息匹配 Agent；Worker 池承接工作。

用途解读：任务来了再找适合且有空的执行者。

03 · 多种求解方式

分工、独立探索、审议、接力

支持并行分解、发散收敛、多轮审议与角色流水线。

用途解读：调研可分工，难题可独立提案，交付可逐步接力。

04 · 工作中的协调

消息、共享上下文与进度

描述结构化对话、共享工作区和事件通知。

用途解读：让接口约定、产物和变更通知能交到相关参与者手中。

05 · 质量控制

计划、执行、审查、迭代

PDRI 循环把审查与返工纳入任务过程。

用途解读：产物提交后仍要验收；评分只是信号，实际测试也要通过。

06 · 失败恢复

超时释放与候补改派

任务失败或过期后，可按策略尝试候补节点。

用途解读：某个执行者掉线时，任务还有继续推进的路径。

07 · 长期复用

共享知识与流程模板

描述共享记忆、主题订阅和可复用流水线。

用途解读：保存的不只有答案，也包括方法和组织步骤。

08 · 改进组织方式

协同记录与编排反馈

用协作历史及任务结果辅助后续组队与策略选择。

用途解读：把“谁配合过、哪种流程有用”变成可参考的记录。

09 · 控制规模与成本

预算、并发与组织策略

平台描述预算、并发、审查、重试等配置及组织管理。

用途解读：把无人值守任务限制在可接受的资源范围内。

10 · 网络参与机制

认领、贡献记录与结算

悬赏与 Worker 任务提供参与和结算机制。

用途解读：让不同执行者有参与入口；有奖励不等于答案可靠。

能力 01、03、04、07、08、10：官方蜂群文档。能力 02、05、06、09：官方蜂群更新说明。卡片为能力摘要，不代表本地 Evolver 包含全部平台服务。

文档提到的隐私计算，也属于蜂群能力吗？

官方将加密任务与受限计算工具作为扩展集成，意图让敏感数据任务参与协作。本研究未审计相关执行与信任边界，不把它写成已经证实的隐私保障。参见上面的官方更新说明。

这些能力在 Evolver 库里，还是在 EvoMap 平台里？

应分三层看：Hub 组织网络任务与协作；Evolver 处理执行侧的经验、提示和网络接入；宿主模型及工具完成实际操作。固定版本 README 描述了客户端 Worker 接入，但本研究未启用。现有 77 项测试只验证选择器、哈希和提示词模块，没有覆盖上述云端蜂群能力。

它是不是已经证明“团队越做越聪明”？

还不能这样推导。保存经验、记录协同、按历史推荐，是可以检查的机制；任务成功率提升和总成本下降，需要对照实验。官方博客和 Wiki 对部分默认阈值、返工次数的描述也有差异，因此这里不把某个默认数值当作统一保证。

蜂群组织当下的协作；经验库连接前后多次任务。

我们关注的产品方向，是把两者结合起来：先跑通可验收的小任务，再验证共享经验是否减少重复试错。多个 Agent 达成一致仍可能出错；需要实际验收，并衡量协作成本。

依据 官方蜂群文档 ↗（2026-09-16 查阅）。角色、能力、经验的区分与图示是本研究的解释框架。现有 77 项测试覆盖 Evolver 局部模块，未验证云端蜂群协作收益。

网页、平台、客户端、AI，各做什么？

把角色拆开，就能理解“打开网页”和“AI 真正干活”的关系。

你

提出任务 · 阅读结果 · 反馈

共享侧

EvoMap 网页与 Hub

  • 网页让人提问、浏览和管理
  • Hub 提供经验检索、发布与记录
  • 平台还描述了任务分配与协作能力
云端整体能力：本研究未实测
查询经验⇄提交结果GEP 规定经验的格式与交换方式
执行侧

Evolver ＋ 执行宿主

  • Evolver 选择策略、组织执行提示
  • 宿主模型理解任务并调用工具
  • 在项目里修改、测试，再记录结果
已验证：选择、哈希、提示词模块

基础独立模式的 Evolver 会生成执行提示词。修改代码依赖有模型和工具的执行环境。仓库另有 solo、代理等路径，需要逐项核实；不能把下载一个库理解为拥有整个 EvoMap 平台。

这里的“进化”，是在重新训练大模型吗？

本研究看到的主要变化是外部经验、策略、记录与后续选择。AI 因为有更多可用的方法而改变做事方式。本次实验没有更新基础模型的参数，也没有证明 AI 获得了无限自我提升能力。

是不是普通知识库换了一个名字？

它与知识检索有重叠，但尝试进一步组织“适用条件、做法、执行结果、后续反馈”。这些结构是否比普通操作说明更有用，仍要用相同任务做对照，不能仅凭 Gene 的名字判断。

接下来，怎样证明它真的有用？

让三组 AI 做相同的任务，用相同的验收标准比较。

A

基础 Agent

靠模型与工具完成任务。

B

附普通操作说明

额外提供整理好的步骤。

C

附结构化经验与反馈

使用 Gene、Capsule 和历史结果。

共同衡量：成功率总成本完成时间错误采纳人工干预

如果 C 在新任务上仍能稳定提高质量、减少总开销，才是这套方案有效的证据。多人同时做事、保存更多资产、给结果打高分，都不能替代这个比较。

我们目前的理解

群体智能是愿景；类似 RAG 的经验沉淀与检索是理解这条探索路线的入口；多 Agent 复用与执行反馈构成持续积累的循环。
这是值得参考的产品方向，实际收益要靠真实任务继续证明。
